# Dedicated Vaultwarden integration fixtures

This helper is test code. It generates **disposable, synthetic accounts** on a
literal-loopback Vaultwarden server, using Python `cryptography` and
`argon2-cffi` to independently exercise the Bitwarden wire format. Production
Veyra never imports it; production vault cryptography uses the pinned official
Rust SDK.

Before making requests, the helper checks public SDK reference vectors for
PBKDF2, Argon2id and HKDF. It then registers two fresh UUID-named accounts,
creates two encrypted login entries in each, and creates a third PBKDF2 account
with real server-side authenticator two-factor authentication. It signs in again,
independently verifies all six encrypted entries and checks rejection of wrong
password hashes. One entry per account uses the account key directly and the
other uses a wrapped per-cipher key. Vault-item TOTP uses the RFC 6238 SHA-1
example secret; account two-factor authentication uses the seed generated by the
dedicated server. Missing-code challenges, rejection of an invalid numeric code
and a successful current-code login are verified against the real server. RSA
private keys, passwords, authenticator seeds and access tokens are never printed.

Use a separate server without real users. The reference image is:

```text
ghcr.io/dani-garcia/vaultwarden:1.37.4@sha256:efb3cde962015fcc036b2ea625242248611943b27212ebf4392841fb30fad055
```

For example, start a disposable local server:

```sh
integration_volume="veyra-local-integration-$(date +%s)-$$"
docker volume create "$integration_volume"
docker run --detach --rm --name veyra-local-integration \
  --cap-drop ALL --security-opt no-new-privileges --pids-limit 256 --memory 512m \
  --mount "type=volume,source=$integration_volume,target=/data" \
  --publish 127.0.0.1:8222:8222 \
  --env ROCKET_ADDRESS=0.0.0.0 --env ROCKET_PORT=8222 \
  --env DOMAIN=http://127.0.0.1:8222 --env WEB_VAULT_ENABLED=false \
  --env SIGNUPS_ALLOWED=true --env SIGNUPS_VERIFY=false \
  --env INVITATIONS_ALLOWED=false --env SHOW_PASSWORD_HINT=false --env LOG_LEVEL=warn \
  --env LOGIN_RATELIMIT_MAX_BURST=1000 --env LOGIN_RATELIMIT_SECONDS=1 \
  ghcr.io/dani-garcia/vaultwarden:1.37.4@sha256:efb3cde962015fcc036b2ea625242248611943b27212ebf4392841fb30fad055
```

The dedicated **named** volume is required: Vaultwarden rejects a missing or
anonymous `/data` volume. It contains only these disposable accounts. The elevated
login rate limit is **only for the isolated integration server**:
the repeated positive/negative tests otherwise exhaust Vaultwarden's default
IP-based bucket. It does not change cryptography or the application policy.
Wait for `/alive` before seeding, then from the repository root:

```sh
python3 -m venv /tmp/veyra-fixture-venv
/tmp/veyra-fixture-venv/bin/python -m pip install -r tests/integration/requirements.txt
fixture_dir=$(mktemp -d /tmp/veyra-fixtures.XXXXXX)
/tmp/veyra-fixture-venv/bin/python tests/integration/seed-vaultwarden.py \
  --server-url http://127.0.0.1:8222 --server-version 1.37.4 \
  --output "$fixture_dir/accounts.json"
export VEYRA_TEST_FIXTURE_FILE="$fixture_dir/accounts.json"
cargo test --locked --manifest-path src-tauri/Cargo.toml \
  vaultwarden::tests::actual_vaultwarden_ -- --ignored
```

The credential manifest must be outside the checkout and is created with mode
`0600`. Existing files are never overwritten. Use `--reuse` with the same
server URL to verify an existing manifest, or choose a new path to create fresh
accounts. Do not upload the manifest as a CI artifact or log its contents.
Delete the temporary fixture directory and stop only your own disposable
container when finished. After stopping this example's container, remove its
dedicated volume with `docker volume rm "$integration_volume"`; never remove a
volume belonging to an existing server.

`serverUrl` identifies the dedicated literal-loopback test origin. The manifest
contains `accounts` with `email`, `password`, `kdf`, and `items`; each item has
`cipherId`, expected fields, and `perCipherKey`. `expected` aliases the first
item for the native test harness. The authenticator account additionally has
`twoFactorSeed` and `twoFactorLastVerifiedStep`, kept only in this protected test
file. `vaultwardenVersion` is the caller's pinned
image version; `serverCompatibilityVersion` is the separately reported
Bitwarden-compatible API version and must not be mistaken for the Vaultwarden
release number.

Vaultwarden prevents successful TOTP time-step reuse, including the code used
to enable an authenticator. The helper preserves that protection. Revalidating
an account may wait once, at most about 30 seconds, for a genuinely new code.
The Rust live test also waits for a fresh time step before its own successful
second-factor login, so repeated test runs do not rely on weakening replay
protection. Activation currently uses the previous time step accepted by the
dedicated server's standard one-step drift allowance.

Both Rust live tests are explicitly ignored during ordinary unit runs. The
command above executes both the personal-vault and authenticator-login tests.
A zero-test or skipped-test run is not evidence of
real server compatibility. The fixture helper supports no production server
URL, stores no real user credentials and cannot validate KDE/GNOME/Wayland or
Flatpak behavior.
