# Connected entry management

The main desktop window can assign existing personal folders, change organization
collections, duplicate entries and move entries between personal and organization
vaults. The backend accepts at most 100 distinct entry references per batch.
Each reference includes the revision displayed when the operation was opened.
Synthetic demo data does not dispatch these operations to a server.

The backend synchronizes before the batch, checks permissions and revisions, and
processes entries sequentially. Folder and collection assignment use the dedicated
Vaultwarden partial endpoints: encrypted item contents remain untouched. Collection
destinations must belong to the entry's organization and allow writing and viewing
passwords. Removing an existing collection also requires permission to modify it.
Organization destinations require at least one accessible writable collection.

Duplicates use a fresh per-item key generated by the pinned official Bitwarden
SDK. The full supported item view includes custom fields, additional URIs and
password history. Attachments, passkeys, opaque encrypted data blobs and fields
unknown to the supported SDK models block copying or changing ownership. The
operation fails explicitly instead of silently dropping those fields; use an
official client for those migrations. Moving within the same owner uses partial
folder/collection assignment and does not re-encrypt payloads.

Editor saves also reject existing entries whose payload fields cannot be
preserved. Favorite changes synchronize first and use the partial endpoint, so
unknown encrypted content remains intact. Partial preference endpoints cannot
atomically compare revisions; their folder/favorite values can still race changes
from another client after the local check.

A personal entry moves into an organization through the authenticated share
endpoint, keeping its ID. Vaultwarden does not allow changing an existing
organization-owned entry to a different owner. That move creates a destination
copy, synchronizes, verifies its complete supported content and destination,
rechecks the original, and only then soft-deletes the unchanged source. It never
permanently deletes the source. If removal fails, the result includes the new
copy's ID and explains whether the source is retained or its removal is uncertain.

Batches and cross-owner moves are **not atomic server transactions**. Folder,
collection and soft-delete endpoints have no revision compare-and-set; another
client can race the last local check. The share endpoint applies Vaultwarden's
existing timestamp tolerance. Known permission/conflict failures are reported per
entry. An uncertain dispatched mutation or failed refresh stops the batch, marks
remaining entries `not_attempted` and blocks further writes until an explicit
successful synchronization. No dispatched mutation is automatically retried.
An accepted copy whose destination is missing or differs after synchronization
also re-enables that write gate and stops the remaining batch.
Locking cancels pending work and prevents its result from publishing metadata to
a newer session.

The dedicated integration test
`actual_vaultwarden_batch_folder_copy_owner_moves_and_partial_results` exercises
real Vaultwarden 1.37.4 folder assignment, fresh-key duplication with custom fields
and multiple URIs, collection replacement, personal-to-organization transfer,
verified organization-to-personal copy plus source soft-delete, stale revisions,
and partial results. A controlled management response verifies that even a 4xx
stops the remaining batch and gates subsequent writes. The server and credentials
are disposable synthetic fixtures; see
[the fixture instructions](../tests/integration/README.md). Passing these checks
does not approve a release or establish production security.

Additional live tests store a synthetic future encrypted login field on the
dedicated server and verify that editor/copy operations reject it while favorite
changes preserve it. Controlled write/sync responses also cover missing and
content-mismatched destinations after accepted copies. These latter responses
simulate failure states rather than claiming those failures were emitted by
Vaultwarden itself.
